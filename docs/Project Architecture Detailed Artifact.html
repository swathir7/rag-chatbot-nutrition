Nutrition Bot

A RAG chatbot that answers nutrition and food-safety questions from 22 official guideline documents, with a citation on every claim.

The 30-second answer

Offline, a Python pipeline parses 22 guideline PDFs into Markdown, splits them by section heading into 563 chunks, and embeds each chunk. At request time, a Next.js backend first blocks medical and calorie questions with regex. It then embeds the question locally, scores it against every chunk stored in SQLite, keeps the top 3, and declines if none scores 0.75 or higher. Otherwise Groq's gpt-oss-120b writes a JSON answer from those chunks only. Zod validates it, and the server overwrites every citation with the metadata of the chunk it came from. Everything runs in one Docker container on Render's free tier.

GroundedThe model only sees retrieved chunks. Its own knowledge is not a source.
Cited by the serverPublisher, year and link come from the database, not from the model's output.
Refuses in two waysOut of scope is blocked in code. A topic the documents don't cover gets a "not covered" answer.

Architecture

Two halves joined by one SQLite file

The index is built once, offline, in Python. The file it produces is copied into the Docker image, and the Node server reads it on every question. Only one call leaves the container: the call to Groq.

Sample questions
    Ingestion

    How the index gets built

    Python scripts run once, on a laptop. Their output is the chunks and documents tables in nutrition-bot.db, which ships inside the Docker image.

    1. Collect

      corpus/raw · generate_metadata.py

      22 files: 21 PDFs and the WHO fact sheet as HTML. 18 are FoodSafety.gov pages, plus WHO, EFSA, NHMRC Australia and the UK Eatwell Guide. metadata.json records publisher, year, source URL, retrieval date and type (18 food safety, 4 nutrition).

    2. Parse

      scripts/parse_documents.py

      pymupdf4llm converts PDFs to Markdown, so headings and tables survive. BeautifulSoup handles the HTML. Table of contents, references, glossary, appendix and acknowledgements sections are dropped.

    3. Chunk

      scripts/build_index.py

      Split on Markdown headings, so every chunk keeps its section name for citations. A section over 800 tokens is split by paragraph, then by line, then by raw tokens with 100 tokens of overlap (tiktoken cl100k_base).

    4. Embed

      sentence-transformers

      jinaai/jina-embeddings-v2-small-en, 512 dimensions. Max sequence length is capped at 1,024 to save RAM, with a batch size of 16.

    5. Store, then migrate

      Chroma → migrate.py

      Vectors and metadata go into Chroma (HNSW, cosine). migrate.py then copies every chunk and vector into the SQLite chunks table, with each vector stored as JSON text. seed_documents.py fills documents.

    6. Ship

      Dockerfile · start.sh

      The 8.3 MB database is copied into the image. If a persistent disk is mounted, start.sh seeds it from that copy on first boot.

    What the chunking strategy cost

    • In the chunking evaluation, 75% of chunks came from the forced-split fallback, because sections in the long PDFs run past 800 tokens. Tables in those sections can be cut mid-row.
    • The Australian guidelines PDF exposed no Markdown headings. All 262 of its chunks have the section name "General", so citations from it can't name a section.
    • The UK Eatwell Guide is mostly an infographic. It parsed to 168 characters, so the index holds one chunk for it.
    Data

    One database, two jobs

    The schema is created on first connection with CREATE TABLE IF NOT EXISTS, so a new disk sets itself up.

    Knowledge: built offline, read at request time

    Filled by the ingestion scripts. The server only reads these tables.

    documents 22 in corpus
    doc_id PK · document_name · publisher · year · source_url · retrieval_date · doc_type (nutrition | food_safety)
    chunks 563 rows
    id PK · doc_id FK · document_name · publisher · year · section_heading · content · chunk_index · token_count · embedding (JSON array of 512 floats)

    App state: written on every request

    Saved in one transaction per question, then pruned to the newest 150 sessions.

    sessions
    id PK · created_at
    messages
    id PK · session_id FK, cascade delete · role (user | assistant) · content (JSON: {text} or the full response) · created_at · index on (session_id, created_at)
    failure_log
    id PK · question · category · response_json · failure_types · run_at

    journal_mode = DELETE instead of WAL, because WAL caused crashes on network-attached disks. Foreign keys are on. better-sqlite3 is synchronous, and one connection serves the whole process.

    Where the 563 chunks come from

    Two long PDFs make up nearly three quarters of the index. Retrieval sees more of them, which is one reason a UK Eatwell question came back with Australian guidance in the evaluation.
